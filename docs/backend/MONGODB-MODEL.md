# MongoDB persistence model

Status: proposed design for NestJS and MongoDB; implementation and database tests have not been performed.

Read with the [backend architecture](README.md), [delivery plan](DELIVERY-PLAN.md), [API plan](API-PLAN.md), and [source requirements](../redesign/BACKEND-REQUIREMENTS.md).
The user's MongoDB selection replaces the source document's relational-database proposal. Its authorization, financial, scheduling, and retention requirements remain applicable.

## 1. Deployment and representation

- Use a MongoDB replica set in development, integration testing, staging, and production. A standalone MongoDB instance is insufficient for this transaction design.
- Use one database per environment and an unsharded initial deployment. Revisit sharding only after measuring contention and defining transaction/shard placement.
- Short business transactions use primary reads, snapshot read concern, and majority write concern. Configure bounded retries and timeouts.
- `_id` is an opaque UUID string generated by the server. Public DTOs expose it as `id`; consumers must not parse identifiers for business meaning.
- Common fields are `createdAt`, `updatedAt` as BSON Date, and an integer `version` for mutable domain documents. Append-only records need no artificial update version.
- Store instants as BSON Date and serialize as RFC 3339 UTC strings ending in `Z`. Use millisecond precision consistently.
- Store date-only values as validated `YYYY-MM-DD` strings. Store IANA timezone names separately; never convert a date-only value into midnight UTC.
- Recurring rules store local wall-clock times and timezone identifiers. Confirmed occupancy stores resolved UTC instants.
- Store money in BSON signed 64-bit integers in minor units. Map it to `bigint` in the domain layer, with explicit BSON conversion in repositories.
- The current API exposes integer JSON amounts: reject values outside `0..Number.MAX_SAFE_INTEGER` before serialization or ingestion. Never silently coerce a larger integer to Number.
- Use integer/rational arithmetic with a documented currency scale and rounding rule. No binary floating-point arithmetic for totals, taxes, or refunds.
- Currency is a lowercase ISO 4217 code from firm/provider configuration; zero-decimal and other supported scales must work.
- Validate schemas in both DTO/domain code and MongoDB collection validators. Reject unknown write fields, disallow arbitrary MongoDB operators, and explicitly allow internal database fields.
- Treat schema version, optimistic domain version, pricing version, and policy version as distinct concepts.

## 2. Collection ownership and schema

Fields below supplement common fields. Optional fields are marked `?`. References use the target's opaque `_id`.
Arrays embedded below are deliberately bounded. Unbounded histories, sessions, appointments, events, and attempts remain separate documents.

### Identity

**`users`** — Identity module.
- `email`, `emailNormalized`, `givenName`, `familyName`, `preferredLanguage`, `timeZone`, `phone?`.
- `passwordHash`, `emailVerifiedAt?`, `status: active|disabled`, `authEpoch`, `securityRevision`, `actionTokenGenerations: {verifyEmail, resetPassword}`, `schemaVersion`.
- `authEpoch` increments after password reset, disabling an account, or changing privileges. Session authorization compares its captured epoch with the current user epoch.
- Email normalization must be one documented function; do not invent provider-specific alias or dot normalization.

**`sessions`** — Identity module; includes anonymous CSRF bootstrap sessions.
- `tokenHash`, `userId?`, `authEpoch?`, `csrfTokenHash`, `authenticatedAt?`, `mfaVerifiedAt?`.
- `lastSeenAt`, `idleExpiresAt`, `absoluteExpiresAt`, `revokedAt?`, `purgeAt`, minimal security metadata.
- `lastPasswordAuthenticatedAt?`, `mfaCredentialId?`, `mfaExpiresAt?`; staff assurance expires independently of the ordinary session.
- Raw session identifiers exist only in cookies/in-memory handling. Runtime authorization checks both expiries and revocation, regardless of document presence.
- Rotate the identifier and CSRF binding after authentication; revoke the replaced anonymous/authenticated session.

**`actionTokens`** — Identity module.
- `userId`, `purpose: verifyEmail|resetPassword`, `tokenHash`, `issuanceId`, `deliveryJobId`, `generation`.
- `expiresAt`, `consumedAt?`, `invalidatedAt?`, `purgeAt`.
- Mail workers generate a random token in memory, store its hash, and send it. A retry after losing the token can issue a fresh token in the same logical delivery group.
- Consuming a token invalidates its siblings for that purpose/generation atomically; retries can deliver duplicate messages, but cannot permit repeated reset/verification effects.
- Token delivery records contain identifiers, never raw tokens or action URLs. Account/purpose generation checks prevent obsolete delivery jobs from issuing usable tokens.
- Issuance and consumption first increment the user's `securityRevision` in a transaction; consumption updates the purpose generation, relevant identity state and session epoch where required.

**`roleAssignments`** — Identity module.
- `userId`, `role: client|lawyer|admin`, bounded `permissions`, `scope: {kind, id}`, `grantedBy`, `grantedAt`, `revokedAt?`, `active`.
- Persist explicit scope sentinels for firm-wide grants; avoid inconsistent missing/null scope identities.
- Public registration creates only the client assignment. Role changes update `users.authEpoch` and append an audit event in the same transaction.

**`firmAuthorizationGuards`** — Identity module.
- Pre-create one singleton `{_id: "firm", revision, updatedAt}` for controlled bootstrap, access grants, offboarding and recovery-admin safeguards.
- Identity mutations that can change the count/availability of recovery administrators increment this guard first, then affected users' `securityRevision` in sorted user-ID order; count current eligible administrators and commit grants/revocations/audit together.
- This identity protocol does not mix booking catalogue/schedule/financial guards. It prevents concurrent administrators from removing the last recovery administrator through independent writes.

**`webauthnCredentials`** — Identity module; public verification material only.
- `userId`, `credentialId` as canonical base64url, `publicKey` as BSON binary, `userHandle`, `rpId`, `signCount`, `transports`, `backupEligible`, `backedUp`, `enrolledAt`, `lastUsedAt?`, `revokedAt?`.
- A maintained WebAuthn implementation verifies origin/RP binding, user verification, signature/counter semantics and ownership. Authenticator private keys are never stored.

**`webauthnChallenges`** — Identity module.
- `userId`, `sessionId`, `purpose: enrollment|authentication`, `challenge`, `rpId`, allowed origin binding, `invitationId?`, `authEpoch`, `expiresAt`, `consumedAt?`, `purgeAt`.
- Bind the single-use random challenge to the initiating session/user/purpose. Consume atomically after valid verification; check deadline and current epoch independently of TTL.

**`mfaEnrollmentInvitations`** — Identity module; controlled initial enrollment/recovery.
- `userId`, `tokenHash`, `grantedBy`, `reasonCode`, `authEpoch`, `expiresAt`, `consumedAt?`, `revokedAt?`, `purgeAt`.
- Enrollment requires this invitation plus recent password authentication, or fresh existing MFA. An invitation does not grant a staff role; reset revokes credentials and sessions with an audit event.

### Catalogue and lawyers

**`topics`** — Catalogue module; API-compatible name for approved consultation services.
- Bounded `translations: {locale: {title, summary, detail}}`, `practiceArea`, bounded `jurisdictions` with approved labels/copy.
- `publicationState: draft|published|retired`, `languages`, `consultationModes`, `durationMinutes`, `checkoutCurrency`, `intakePolicyVersion`, `policyVersion`.
- Rich detail uses the approved sanitized format. Names, geography, language, and nationality never imply jurisdiction coverage.
- `activePriceIds` is a bounded list of explicit current prices by configured pricing key; all referenced prices must belong to this topic.
- MVP permits one `checkoutCurrency` per topic and exactly one active positive-total price per allowed duration; lawyer/mode pricing and multi-currency selection stay disabled pending a contract increment.

**`lawyers`** — Catalogue module with Scheduling participation for eligibility changes.
- `userId`, `displayName`, bounded approved `translations`, `credentials`, `languages`, `consultationModes`, `timeZone`, `active`.
- Bounded `serviceEligibility: [{topicId, jurisdictionIds, durationMinutes, languages, consultationModes, active, version}]`.
- Domain validation enforces one entry per topic and capability intersections. A multikey unique index does not enforce uniqueness of array entries inside one document.
- Because clients cannot select a jurisdiction, an eligible lawyer must cover every jurisdiction advertised by the topic. Partial jurisdiction matching stays disabled until a reviewed selection/eligibility contract exists.
- Public profile DTOs use an explicit field allowlist; internal user linkage and authorization fields are never returned publicly.

**`lawyerPrivateProfiles`** — Identity/operations-owned restricted metadata.
- `lawyerId`, approved operational fields only, with independent authorization. Legal intake never belongs here.

**`servicePrices`** — Catalogue module; immutable published pricing versions.
- `topicId`, `pricingKey`, `priceVersion`, `durationMinutes`, `currency`, `lawyerScope`, `modeScope`.
- `subtotalMinor`, tax configuration reference, `effectiveFrom`, `effectiveUntil?`, `publishedAt`, `supersedesPriceId?`.
- `pricingKey` comes from a canonical tuple; `lawyerScope=all` and `modeScope=all` are explicit sentinels when pricing is not specialized.
- In MVP these sentinels are mandatory and `currency=topics.checkoutCurrency`; future dimensional fields do not authorize enabling unsupported frontend choices.
- Serialize activation/retirement and effective-range validation with the topic catalogue guard. A unique index cannot detect overlapping effective-date intervals.
- Retire through catalogue selection/history, without rewriting amounts already referenced by quotes. Future price scheduling needs an explicitly versioned activation record/workflow.
- MVP price activation is immediate-only: assign `effectiveFrom` from trusted server time under the catalogue guard. The API accepts no writable future or backdated activation timestamp.

**`noticeDrafts`** — Catalogue module; mutable, unpublished authoring records.
- `kind: privacyNotice|terms`, bounded `workflows: [registration|booking]`, `locale`, `title`, `content`, `format`, `approvalReference?`, `version`.
- Publishing checks the expected draft version and firm approval, then inserts an immutable published version; it never changes content previously accepted by clients.
- MVP notice publication/activation is immediate-only; the server assigns `publishedAt` and `effectiveFrom`. The API accepts no writable future or backdated activation timestamp.

**`policyVersions`** — Catalogue module; append-only approved policy/notice versions.
- `kind`, `policyKey`, `policyVersion`, `locale`, `title`, `content`, `format`, bounded `workflows`, `approvedAt`, `approvedBy`, `approvalReference`, `publishedAt`, `effectiveFrom`, `contentHash`.
- Development policies are visibly synthetic. A version is valid for acceptance only when the approved content is actually presented.
- Published notices remain retrievable by kind/version/locale. Workflow configuration selects required/accepted published versions; old acceptance records are never rewritten when that selection changes.

**`noticeRequirements`** — Catalogue module; current workflow configuration.
- `workflow: registration|booking`, `locale`, bounded `required: [{kind, currentVersionId, acceptedVersionIds}]`, `version`.
- Publication updates this selection with optimistic version checks. Acceptance records the configuration version and exact immutable notice versions used by the transaction.

**`acknowledgementEvents`** — Identity/Intake publish; append-only consent evidence.
- `actorClientId`, `workflow: registration|booking`, `bookingId?`, `noticeRequirementsVersion`, bounded `notices: [{kind, policyVersionId, version, locale}]`, `acceptedAt`, `acceptanceKey`, `requestId`.
- Registration acknowledgements commit with the new client; booking acknowledgements commit with intake updates. Both validate actual published content/workflow/locale, not environment version strings alone.

### Scheduling

**`catalogueGuards`** — Catalogue module.
- `_id=topicId`, `revision`, `updatedAt`; created in the same transaction as the topic and retained throughout its lifecycle.
- Reservations and publication/active-price edits write this shared document before checking or changing relevant catalogue state.

**`scheduleGuards`** — Scheduling module.
- `_id=lawyerId`, `revision`, `updatedAt`; created with the lawyer and retained after deactivation.
- All interval mutations and lawyer eligibility/schedule mutations write this guard. There is one guard per lawyer, not one per start time or calendar date.

**`availabilityRules`** — Scheduling module.
- `lawyerId`, `ruleSetVersion`, `timeZone`, `effectiveFromDate`, `effectiveUntilDate?`, `active`.
- Bounded `weeklyWindows: [{weekday, startLocal, endLocal, endDayOffset}]`, breaks, buffer minutes, lead-time reference, explicit DST expansion policy.
- Rules are wall-clock data. Validation rejects impossible/overlapping definitions or resolves them through one documented expansion function.

**`availabilityExceptions`** — Scheduling module.
- `lawyerId`, `kind: unavailable|extraOpening`, `startAt`, `endAt`, `reasonCode`, restricted `staffNote?`.
- Store resolved UTC intervals, including cross-midnight exceptions. Do not expose private reasons in public availability.

**`occupancies`** — Scheduling module; authoritative active reservations.
- `_id=bookingId`, `lawyerId`, `bookingId`, `state: held|confirmed`.
- `startAt`, `endAt` are consultation instants; `occupiedStartAt`, `occupiedEndAt` include snapshotted buffers.
- `bufferBeforeMinutes`, `bufferAfterMinutes`, `holdExpiresAt?`, `bookingVersion`.
- One document represents the currently occupied interval for a booking. Remove it when expired/cancelled, preserving history in the booking/audit records.
- Keep confirmed occupancy through appointment closure; do not remove it based on an uncoordinated TTL or background delete.

**`slotOffers`** — Scheduling module; short-lived advisory availability bindings.
- Generate 32 cryptographically random bytes and return their 43-character base64url encoding as `slot.id`, within its existing 128-character limit. Store only its SHA-256 hash as this collection's `_id`.
- `topicId`, `lawyerId`, `durationMinutes`, `language`, `consultationMode`, `timeZone`, `startAt`, `endAt`, `topicVersion`, `eligibilityVersion`, `scheduleVersion`, `priceVersion`, `expiresAt`, `purgeAt`.
- Hash the supplied ID, check explicit expiry and every binding, then revalidate current eligibility/price/availability under guards. An offer is never an occupancy or promise to reserve time.

### Bookings and intake

**`bookings`** — Booking module.
- `clientId`, `topicId`, `lawyerId`, `startAt`, `endAt`, `durationMinutes`, display `timeZone`, `language`, `consultationMode`.
- `status: pendingPayment|confirmed|expired|cancelled|completed|noShow`, `holdExpiresAt?`, `version`.
- Embedded bounded `quote: {quoteVersion, priceId, priceVersion, currency, subtotalMinor, taxMinor, totalMinor, taxLines, policyVersion, issuedAt, expiresAt}`; initially `quote.expiresAt=holdExpiresAt`.
- Embedded `policySnapshot` includes applicable version IDs, reservation buffers, lead-time and cancellation calculation inputs needed for later decisions.
- `cancelledAt?`, `cancellationReasonCode?`, restricted `cancellationNote?`, `completedAt?`, `noShowAt?`, `resolutionRequired`, `resolutionCode?`.
- Optional derived `paymentStatus`, `refundStatus`, `paidMinor`, `refundedMinor` are maintained transactionally by Payments; attempts/refunds remain the financial evidence.
- Quotes are immutable once issued for the hold. Changed price/duration/service requires a new explicitly accepted quote through a reviewed replacement workflow.
- The proposed equal-price staff reschedule preserves the original paid quote and acceptance history; validate an equal-total replacement price without rewriting the paid quote. Other adjustments remain out of MVP scope.
- Booking lists omit intake text, provider client secrets, operational notes and sensitive audit metadata.

**`intakes`** — Intake module.
- `bookingId`, `clientId`, `summary?`, `preferredLanguage`, `submittedAt`, `version`.
- Bounded `acknowledgements: [{kind, noticeVersionId, acceptedAt, acceptedByClientId}]` only for notices actually shown and actively accepted.
- This bounded list is a current projection of immutable `acknowledgementEvents`; registration consent is stored independently of intake.
- Only the owner submits client acknowledgements. Staff cannot fabricate acceptance by editing intake.
- Owner/assigned lawyer/explicitly permitted staff access is checked against current relations. Privileged reads create durable audit events without narrative content.
- Intake edit limits and retention are policy gates; there is no automatic intake TTL.

### Payments and refunds

**`financialGuards`** — Payments module.
- `_id=bookingId`, `revision`, `updatedAt`; created with the booking.
- Every attempt replacement, payment application, refund allocation and financial aggregate repair writes this guard before reading/mutating related financial state.

**`paymentAttempts`** — Payments module.
- `bookingId`, `quoteVersion`, `provider`, `providerAccountId`, `environment`, `providerIntentId?`, `providerIdempotencyKey`.
- `amountMinor`, `currency`, `status`, `providerStatus?`, `isPayable`, `creationState: pending|created|reconciliationRequired`.
- `lastSynchronizedAt?`, `failureCategory?`, `providerPaidAt?`, `version`.
- `executionStatus`, `nextAttemptAt`, `attemptCount`, `leaseOwner?`, `leaseUntil?`, `leaseGeneration` fence durable provider-creation/reconciliation execution.
- Only one effective payable attempt exists for a booking/quote. Replacement retires the prior attempt under a reviewed provider cancellation/reconciliation barrier.
- A reusable failed intent can remain payable; failure is not universally terminal. Verified success cannot be overwritten by a delayed failure event.
- Store no raw card data or persistent client secret. Retrieve narrowly scoped frontend SDK details for the authenticated owner when needed.

**`refunds`** — Payments module.
- `bookingId`, `paymentAttemptId`, `amountMinor`, `currency`, `reasonCode`, `requestedBy`, `requestedAt`.
- `provider`, `providerAccountId`, `environment`, verified against the referenced attempt.
- `status: pending|succeeded|failed`, `providerRefundId?`, `providerIdempotencyKey`, `lastSynchronizedAt?`, `failureCategory?`, `version`.
- `executionStatus`, `nextAttemptAt`, `attemptCount`, `leaseOwner?`, `leaseUntil?`, `leaseGeneration` fence refund execution and retries.
- Under the financial guard, reserve requested amounts against captured funds minus successful and pending refunds.
- Unknown remote outcomes remain pending/reconciliation-required. Mark failed and release reserved funds only when the outcome is definitive.
- Refund completion does not change the historical succeeded payment into a failed payment.

**`providerInbox`** — Payments module.
- `provider`, `providerAccountId`, `environment`, `providerEventId`, `eventType`, `providerObjectId`, `receivedAt`.
- `status: pending|processing|processed|ignored|failed`, `attemptCount`, `nextAttemptAt`, `leaseOwner?`, `leaseUntil?`, `leaseGeneration`, `processedAt?`, safe `lastErrorCode?`.
- Persist only after raw-body signature verification. Store durable receipt identities; optional encrypted raw payload storage has separate approved retention.
- Verify account/environment, object/booking relation, amount and currency before applying any state. Mismatches create operations cases.

### Jobs, operations, and auditing

**`outbox`** — Owning module publishes; worker delivers.
- `businessEventKey`, `kind`, `aggregateId`, `recipientUserId?`, `locale`, `templateVersion`, minimal `payload`.
- `status: pending|processing|sent|failed`, `attemptCount`, `nextAttemptAt`, `leaseOwner?`, `leaseUntil?`, `leaseGeneration`, `deliveryProviderId?`, `sentAt?`.
- Insert in the domain transaction. Poll/claim with atomic conditional updates and durable leases; MongoDB is the initial job store, with no required Redis dependency.
- A send followed by a crash creates uncertainty; reconcile delivery identifiers when possible. Do not claim exactly-once email delivery.
- Reminder jobs include booking/version references and recheck current status/time before sending. No legal narrative, token, or provider secret belongs in payloads.
- Lease claim/takeover increments `leaseGeneration`; success/error acknowledgement matches `_id`, `leaseOwner` and the claimed generation. Stale executors cannot overwrite newer local outcomes.

**`operationsCases`** — Operations module.
- `caseKey`, `kind`, `bookingId?`, `paymentAttemptId?`, `refundId?`, `status`, `reasonCode`, `assignedTo?`, `resolvedAt?`, `resolutionCode?`, `version`.
- Durable cases cover late payment, amount mismatch, failed refunds, persistent mail failures, and ambiguous reconciliation. Do not rely on logs as a work queue.

**`jobs`** — Platform/owning module; bounded maintenance and accepted operation work.
- `jobKey`, `kind`, `aggregateId?`, safe identifier-only `payload`, `status`, `nextAttemptAt`, `attemptCount`, `leaseOwner?`, `leaseUntil?`, `leaseGeneration`, `completedAt?`, safe `lastErrorCode?`.
- Use for expiry/reconciliation scans and accepted operational commands; provider attempts and notification outbox entries retain their own durable execution state. References connect each operation receipt to the corresponding job/case.
- Claim and acknowledge with the same fenced generation protocol; retries call domain services and never bypass guard/permission rules.

**`idempotencyRecords`** — Request infrastructure with domain transaction participation.
- `actorId`, `operation`, `key`, `requestHash`, `state: running|completed`, `resultStatus?`, safe `resultBody?`, `resourceId?`, `expiresAt`, `purgeAt?`.
- `nextAttemptAt`, `attemptCount`, `leaseOwner?`, `leaseUntil?`, `leaseGeneration`; include target resource in the canonical operation scope.
- Retain completed booking/cancellation results; payment responses store safe reconstruction metadata rather than provider client secrets.
- The proposed retention is 24 hours, subject to the published contract. After expiry, key reuse may execute anew; permanent domain/provider uniqueness remains independent.
- In-progress leases/recovery must verify existing domain effects before taking over. Same key with different canonical input returns an idempotency conflict.
- Set `purgeAt` only after completion. Unresolved records survive the replay window; atomically replace an expired completed record under its unique key when needed, independently of TTL timing.

**`auditEvents`** — Audit infrastructure; append-only through application permissions.
- `actor: {kind, id}`, `action`, `targetType`, `targetId`, `occurredAt`, `reasonCode?`, `requestId`, safe `before?`, safe `after?`.
- Capture staff intake reads, role changes, overrides and financial actions. No password, cookie, token, secret, or legal narrative is permitted.

All TTL indexes above use a single BSON Date field and `expireAfterSeconds:0`; `purgeAt` includes any approved post-expiry diagnostic retention.
Optional unique keys use partial indexes, not a plain unique nullable field. Add indexes only for approved queries, and avoid parallel-array compound multikey designs.
Indexing both interval endpoints helps filtering but does not create an interval exclusion constraint; the guard protocol establishes exclusivity.

## 4. Transaction and concurrency invariants

1. Identify candidate topic/lawyer/booking IDs without trusting the pre-read values as authoritative.
2. Begin a transaction. Acquire guards by incrementing `revision` in this global order: sorted topic `catalogueGuards`, sorted lawyer `scheduleGuards`, sorted booking `financialGuards`.
3. Re-read and validate all authoritative relations and versions inside the transaction. If the required guard set changed, abort and restart with the correct set.
4. Missing pre-created guards are an integrity failure, not permission to continue without serialization. Provision them with their parent records.
5. Include every relevant elapsed hold's booking financial guard in the initially discovered lock set. Under lawyer/financial guards, re-read the overlaps, restart if that set changed, then atomically expire the holds and remove occupancy before admitting a conflicting reservation.
6. Reject overlap when `existing.occupiedStartAt < proposed.occupiedEndAt` and `existing.occupiedEndAt > proposed.occupiedStartAt`. Half-open adjacent intervals can coexist.
7. Create/update booking, occupancy, financial evidence, audit/outbox event, and applicable idempotency outcome in the same local transaction.
8. Confirm only when the booking is still pending, its hold is valid, its matching occupancy exists, and verified payment matches its quote. Released intervals cannot be reclaimed by a late event.
9. Cancellation/expiry release occupancy together with the booking transition. Keep paid/refund evidence and create any resolution task in that same transaction.
10. Staff reassignment holds both old/new lawyer guards in sorted order and secures the replacement interval before removing the old occupancy.
11. Financial mutations reserve pending refunds and maintain aggregate amounts while holding the booking financial guard. Mixed scheduling/financial transitions use the complete global lock order.
12. Staff edits use conditional `{_id,version:expectedVersion}` writes with `$inc:{version:1}`; a mismatch returns `409` or the agreed precondition response. Guard revisions do not replace public optimistic versions.

Use a trusted server/database time source for validity checks and a controllable clock for tests. Never use client time or stale cleanup state to determine expiry.
Transaction callbacks can execute more than once: no email, provider calls, logs containing secrets, or other external effects inside them. Persist stable IDs and retry intent outside callback-local randomness.
MongoDB's documented shared-document write-conflict behavior supports this serialization mechanism; its correctness still depends on every writer following the protocol and on real-database race tests. [MongoDB transaction considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/).
MongoDB TTL cleanup is asynchronous. It is appropriate for eventual removal of expendable records, not immediate session revocation, token consumption, interval release, or financial correctness. [MongoDB TTL indexes](https://www.mongodb.com/docs/manual/core/index-ttl/).

## 5. References, migrations, and retention

- MongoDB provides no relational foreign keys. Owning modules validate reference existence, current permissions and matching relationships inside the relevant transaction.
- Configure infrastructure encryption at rest, TLS and encrypted backups. Give API, worker and migrations distinct database credentials with only their required privileges.
- Client, topic, lawyer, booking, quote, attempt and refund IDs are immutable. Deactivate catalogue/staff records instead of cascading deletion through booking or financial history.
- Intake and identity deletion/export require separate firm-approved policies; financial evidence and audit retention are independent decisions. No booking, occupancy, payment, refund, inbox identity, outbox business identity, intake, or audit TTL is proposed.
