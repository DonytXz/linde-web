# Backend requirements for the law firm booking product

> Historical planning baseline. The frontend redesign has since been implemented; see [Frontend handoff](../FRONTEND-HANDOFF.md) and [Migration record](../MIGRATION-RECORD.md) for current status. Backend implementation is outside this delivery. Legacy source citations below refer to the preserved recovery snapshot, not the new source tree.

Status: proposed implementation baseline, prepared 2026-09-26 and updated to remove location-specific positioning. The owner confirmed a law firm consultation product with an immigration-law focus. This document distinguishes code observed locally from requirements for a new backend. No deployed API, production database, provider account or legacy customer records were inspected.

Read alongside the [redesign plan](REDESIGN-PLAN.md), [draft client API](openapi.json) and [parallel kickoff](PARALLEL-KICKOFF.md). The API file covers the initial client interface; the operational and staff requirements below still require a subsequent contract increment. Reconcile and version both documents before implementation.

## 1. Scope and decisions

The core product is discovery of the firm's approved services, account creation, booking an eligible lawyer, minimal consultation intake, payment, confirmation and management of appointments. Staff must be able to operate schedules and handle booking/payment exceptions. Spanish is the proposed default, English the first-release alternative. Each office/lawyer schedule has an explicitly configured IANA timezone; stored appointment instants use UTC and clients may display another IANA timezone. No city or region determines a production default.

The service catalogue must explicitly say which jurisdiction each service covers and which lawyers are eligible. Service coverage, licensing descriptions and offered services require firm-approved metadata and copy; they must not be inferred from office location, client location, language or nationality. The system does not determine immigration eligibility, provide automated legal advice, predict case outcomes, or imply legal representation merely because someone books a consultation. Full case management and document uploads are outside this MVP.

The firm must supply the lawyer roster, approved practice areas/jurisdictions, languages, consultation modes, service durations, prices/currency, taxes/invoice handling, lead times, cancellation/refund terms, required intake and any pre-booking conflict-screening policy. Until supplied, development uses explicitly synthetic fixtures. Policy-dependent acceptance gates stay open; developers must not invent customer-facing terms.

Proposed implementation shape: one modular API, one relational database and a background worker. Identity, catalogue, scheduling, bookings/intake, payments and notifications are separate modules with explicit ownership. Framework, hosting and provider selection remain implementation decisions. A new backend project can start from these contracts independently of visual design or final branding.

## 3. Roles and authorization

| Principal | Allowed baseline operations | Limits |
| --- | --- | --- |
| Visitor | Read published services, approved lawyer metadata and available slots; register, verify/recover access, bootstrap CSRF | No client records, private schedules or identity-bearing availability responses |
| Client | Read/update own basic profile; create/read own bookings; edit permitted intake; start/resume own payment; cancel under policy | Cannot set price, owner, assigned lawyer outside eligibility, payment state, roles or booking status |
| Lawyer | View assigned appointments and their minimum necessary intake; manage own availability if firm policy permits; mark assigned consultations completed/no-show | No unrelated client intake or payment administration by default |
| Administrator | Manage catalogue, lawyer eligibility, schedules, booking assignments, cancellation/refund exceptions and account administration | Operational metadata access does not automatically include legal-intake content; an explicit permission is required |
| Worker/provider integration | Perform narrowly scoped verified payment/job transitions | No interactive staff rights; separate service credentials and audit identity |

Enforce permissions on every object read and mutation, including nested resources, exports and staff search. Return a non-disclosing 404 for a client's attempt to access another client's resource. Record privileged intake reads, staff overrides, role changes and financial actions with actor, time, reason and correlation ID. Grant staff access through a controlled administrator process; public registration always creates a client. Staff authentication must support an additional factor before production administration is enabled.

## 4. Authentication and session contract

- Provide register, email verification/resend, login, logout, current user (`GET /v1/me`), forgot-password and reset-password operations. Verification and reset links are single-use, expiring, cryptographically random tokens stored only as hashes. Never log these tokens or passwords. Only verified accounts can reserve/pay for appointments.
- Normalize emails consistently and enforce uniqueness in the database. Preserve display names separately from email identity. Store passwords with a maintained adaptive password hash implementation; configure and benchmark its cost. Allow password managers and long passphrases; define a sensible maximum input size and reject common/compromised passwords through the chosen identity design.
- Use an opaque server session identifier in a `Secure`, `HttpOnly` cookie, with explicit `Path=/`, no broad Domain attribute and `SameSite=Lax` for the proposed same-site deployment. Rotate sessions after login/privilege changes. Enforce configurable idle and absolute expiry, revoke on logout/password reset, and permit administrative revocation. Do not return bearer tokens for frontend local storage.
- `GET /v1/csrf` bootstraps an anonymous session-bound CSRF token and returns it to the frontend. Require `X-CSRF-Token` plus trusted Origin checks on browser state-changing operations, including login/registration/logout. Rotate/rebind CSRF after authentication and let the frontend bootstrap again. The signed provider webhook is exempt from browser CSRF and uses independent verification.
- Prefer a same-origin proxy or same-site frontend/API deployment. If origins differ, use an explicit CORS allowlist and credentialed requests; never wildcard allowed origins with credentials. Cross-site cookie requirements must be resolved before deployment, including browser cookie restrictions, rather than silently changing the session contract.
- Throttle login, verification/resend, recovery and reservation/payment creation by relevant account/IP/session dimensions. Registration/recovery responses must not disclose whether an address belongs to an account; verification delivery is a queued side effect. Use neutral user-facing messages while keeping structured internal reasons.
- Distinguish unauthenticated `401` from authenticated-but-unverified/forbidden `403`. An ordinary permission denial must not automatically destroy a valid session as the old global handler does.

Proposed development defaults such as session lifetime and hold lifetime must be configuration values and documented in the backend environment example; they are not firm-approved policy.

## 5. Shared API conventions

- Base path `/v1`; JSON request/response fields use `camelCase`; IDs are opaque strings. Clients must not depend on database sequence numbers or parse IDs for business data. Legacy snake_case mappings belong only in a temporary compatibility adapter.
- Instants are RFC 3339 UTC strings ending in `Z`; timezones are valid IANA identifiers. Date-only values remain `YYYY-MM-DD` and are never coerced into midnight UTC. Recurring schedules are local wall-clock rules plus the lawyer's zone, expanded into real instants server-side.
- Money uses non-negative integer minor units and a lowercase three-letter ISO 4217 currency code. The API does not hardcode a country-specific currency pair; the server validates each code against the firm's configured currencies and provider support. Example currencies do not enable production acceptance. Use each currency's minor-unit scale rather than assuming two decimals, and no float arithmetic for price, tax or refunds.
- Collection responses are bounded, consistently ordered and cursor-paginated where records can grow, especially appointments. Enforce query ranges and maximum page sizes. Never return unbounded intake or user collections.
- Standard errors contain a stable machine-readable `code`, readable `message`, `requestId` and optional `fieldErrors`; frontend translations map stable codes. Use `400` for malformed input, `401` unauthenticated, `403` forbidden/unverified, `404` unavailable resource, `409` concurrency/state/idempotency conflict, `422` valid JSON failing field/business validation, `429` rate limit and `503` temporary dependency outage. Preserve the exact wrapper and field names in the shared OpenAPI revision.
- Reject unknown write fields and read-only field assignment. Validate types, enums, lengths, identifiers, ownership, service/lawyer eligibility, allowed durations, pricing versions and timezone values on the server. Rich catalogue text has an allowlisted format; plain intake text is never interpreted as HTML.
- Require `Idempotency-Key` on booking creation, payment-intent creation and cancellation. Scope records to actor + operation + key; save a canonical request hash and completed response. Same key/same input returns the original result, same key/different input returns `409 IDEMPOTENCY_CONFLICT`; concurrent attempts share one execution or receive a retryable in-progress result. Persist idempotency records, not process memory. Publish retention and behavior after expiry; a proposed initial retention is 24 hours, while durable booking/payment uniqueness lasts independently.
- Mutating staff edits use an optimistic version or `If-Match` convention to prevent lost updates. Correlation IDs pass through API, provider adapters and jobs without exposing sensitive payloads.

The draft retains `/v1/topics` as the catalogue route and `topicId` as its reference; a topic now represents a firm-approved consultation service/practice area. This naming does not preserve the legacy wire format. Success objects use `{data: ...}`; lists use `{data: [...], pagination: {nextCursor}}` where paginated.

| Initial client operation | Contract intent |
| --- | --- |
| `GET /v1/topics`, `GET /v1/topics/{topicId}` | Published practice/service metadata, translations, allowed durations and explicit server prices |
| `GET /v1/lawyers/{lawyerId}` | Published lawyer summary, firm-approved credentials, supported services/jurisdictions, languages and consultation modes; no private staff metadata |
| `GET /v1/availability` | `topicId`, `durationMinutes`, `language`, `consultationMode`, `from`, `to`, `timeZone`; returned slot has `id`, `lawyerId`, `startAt`, `endAt`, `expiresAt` |
| `POST /v1/bookings` | `{slotId, topicId, durationMinutes, timeZone, language, consultationMode}`; eligibility, assigned lawyer, quote and hold are determined by server |
| `GET /v1/bookings`, `GET /v1/bookings/{bookingId}` | Owned appointment list and authoritative detail including quote, hold expiry and separate booking/payment/refund state |
| `PUT /v1/bookings/{bookingId}/intake` | `{summary, preferredLanguage, consents: {privacyNoticeVersion, termsVersion}}`; only the owner can submit client acknowledgements |
| `GET /v1/bookings/{bookingId}/intake` | Owner's current minimal intake or null for an unsubmitted intake; private, never cached, supports reload/edit without putting legal text in booking lists |
| `POST /v1/bookings/{bookingId}/payment-intents` | `{bookingVersion}`; no client amount/currency; owner receives existing/new intent details needed by provider SDK |
| `POST /v1/bookings/{bookingId}/cancel` | Optional reason; server checks current state, ownership and policy; duplicate attempts have one business effect |

Slot `expiresAt` is the validity of an offered slot token, not a reservation. Booking `holdExpiresAt` is the reservation deadline. Both must be checked independently at the appropriate operation. The intake contract can carry terms/privacy version acknowledgements only when those notices exist and the UI actually presents them; keep a server-recorded acceptance time and do not infer consent from page navigation. Structured case questions are deferred to a separately reviewed contract increment.

## 6. Persistence model

The following logical entities are proposed, not an assertion about the old database. All records have an opaque `id`, creation/update timestamps and database constraints appropriate to their relations. Store only fields needed for the approved workflow.

| Entity | Required or relevant fields and relationships |
| --- | --- |
| User | `email`, normalized email, password hash or managed-identity reference, `givenName`, `familyName`, `preferredLanguage`, preferred `timeZone`, optional phone, verification/status fields; one user has many sessions and bookings |
| Session / action token | Hashed identifier/token, user or anonymous-session link, expiry, revoked/consumed timestamp, minimum necessary security metadata |
| Role assignment | User, role (`client`, `lawyer`, `admin`), scoped permissions, granting actor/time; cannot be self-edited |
| Lawyer | User relation, firm-approved display name/credentials, languages, service/jurisdiction eligibility, supported consultation modes, schedule `timeZone`, active flag; private staff metadata separated from public profile |
| Practice area / Service | Approved translated title, summary/detail, publication state, practice-area relation, jurisdictions, languages, modes and allowed durations; immigration is offered only with firm-approved scope |
| Service price | Service + duration + currency (+ lawyer/mode only if the firm prices that way), amount, effective dates and immutable version; unique active price for each configured combination |
| Availability rule / exception | Lawyer, local weekdays/hours and IANA zone, effective dates, breaks/buffers, time off and extra openings; no client identity in public responses |
| Booking | Client, service (`topicId` in the API), assigned lawyer, `startAt`/`endAt` UTC, `timeZone` selected for display, `durationMinutes`, language, consultation mode, status, hold expiry, version, cancellation/completion reason/timestamps and pricing/policy snapshot |
| Quote snapshot | Booking relation; currency, subtotal/tax/total minor amounts and pricing/policy version; immutable once payment starts; never computed from client-supplied totals |
| Intake | Booking and client relation; short matter summary, preferred language/contact details only as necessary, submitted/updated timestamps, consent/declaration version where actually required; access separate from ordinary booking metadata |
| Payment attempt | Booking, provider reference, provider intent ID, amount/currency, state, idempotency key, last synchronized time and failure category; no raw card data or reusable provider secrets |
| Refund | Payment relation, requested amount, reason, actor, provider reference, state (`pending`, `succeeded`, `failed`), idempotency identity and reconciliation metadata |
| Provider event inbox | Unique provider event ID, event type, received/processed timestamps, processing state and bounded retry metadata; restricted raw payload retention if needed |
| Outbox / notification | Unique business event/deduplication key, recipient/channel/template/locale, minimum payload, status and retry/sent timestamps |
| Audit event | Actor and action, target IDs, timestamp, reason, request ID and safe before/after metadata; no password, payment secret or legal narrative |

Use foreign keys, uniqueness and transaction constraints to enforce invariants. Time interval exclusivity must be database-enforced or implemented through a proven serializing lock/constraint design, not a preceding availability query alone. Retain cancelled/expired booking and financial records for reconciliation; avoid cascading deletes of financial evidence. Define retention/deletion and encrypted backup handling with the firm before production data collection.

## 7. Scheduling, holds and booking lifecycle

1. **Discover availability.** Query by published service, duration, required consultation language/mode, requested range and client zone. Choose only active eligible lawyers and rules. Return actual UTC slots plus display information, without other clients' identities. Bind eligibility to the offered slot and revalidate when reserving. Bound the search horizon. Availability is advisory until reserved.
2. **Create a reservation.** A verified client selects a server-offered eligible slot. The server revalidates service/duration, lawyer eligibility, lead time, schedule exceptions, no overlap and price. In one transaction reserve the lawyer's `[startAt, endAt)` interval including configured buffers, create a `pendingPayment` booking with immutable quote and `holdExpiresAt`, and persist the idempotent result. Adjacent non-overlapping intervals can coexist. For pooled assignment, select and lock a concrete eligible lawyer before returning success.
3. **Resolve contention.** Two transactions competing for overlapping intervals for one lawyer cannot both succeed. Return `409 SLOT_UNAVAILABLE` for the loser, including a safe retry action. Check expiry using database/server time. Expired holds must cease blocking through an atomic state/lock transition; a delayed cleanup worker must not extend the hold accidentally.
4. **Collect minimal intake.** Allow the owner to supply a short optional summary and preferences before payment. Configure limits and avoid national IDs, immigration documents, date of birth, marital status and nationality as routine booking fields. If the firm requires conflict screening before payment, explicitly add that workflow and acceptance criteria before launch; do not pretend the optional summary implements legal conflict screening.
5. **Pay or expire.** Starting payment does not by itself confirm an appointment or indefinitely extend the hold. A verified successful payment can confirm only under the rules below. A proposed development hold is 15 minutes; the firm must select the real policy. Show expiry to the client and support recovery by obtaining a new available slot/quote.
6. **Manage appointments.** Clients can list/read their bookings, see server-authoritative payment/booking state and cancel under the configured policy. Staff can handle assignment, cancellation, completion/no-show and exceptions with audit reasons. MVP rescheduling may be a staff-assisted atomic operation; never release the old interval before securing the replacement, and never use an unpriced time edit on a paid booking.

| Current booking state | Permitted next state | Actor and invariant |
| --- | --- | --- |
| `pendingPayment` | `confirmed` | Verified payment processing path; quote matches, hold/interval remains valid, exactly one confirmation |
| `pendingPayment` | `expired` | Expiry worker or transactional access path after hold expiry; release interval atomically |
| `pendingPayment` | `cancelled` | Owner/authorized staff; release interval; handle any racing provider payment separately |
| `confirmed` | `cancelled` | Owner under policy or authorized staff override; release interval, record refund eligibility separately |
| `confirmed` | `completed` | Assigned lawyer/authorized staff after appointment time; record audited completion |
| `confirmed` | `noShow` | Assigned lawyer/authorized staff after the defined grace period; policy-gated financial effects |
| `expired`, `cancelled`, `completed`, `noShow` | None in normal client workflow | Do not revive terminal bookings because a delayed event arrives; correction uses a separately audited operational procedure |

Booking status, payment state and refund state are separate facts. A cancelled paid appointment can have a refund pending or no refund due; `expired` does not imply that the provider never charged. Clients must see these distinctions in plain language.

Time-zone acceptance must include configured zones with and without daylight-saving transitions, nonexistent/ambiguous local times, cross-midnight intervals and a client in a different zone. Generate slots from office/lawyer rules and persist real instants; never trust a local timestamp stripped of its offset, as the old submit path does.

## 8. Payment integrity and reconciliation

- Create or reuse a PaymentIntent only for the authenticated owner's `pendingPayment` booking with an unexpired hold. Validate the current booking version, server quote, supported currency and any configured required acknowledgements/intake or screening gate. Optional summary is not a payment gate. Required screening cannot be enabled until its staff workflow and contract exist. Return the provider client secret only to that owner, over TLS, for the provider frontend SDK. No client-provided amount, sample merchandise item, receipt recipient or arbitrary booking ID can change ownership or price.
- Make provider creation idempotent and persist the booking/payment relationship. Provider API calls cannot participate in a database transaction: use a durable attempt record and stable provider idempotency identity to recover after a crash between remote creation and local persistence. Permit at most one effective payable intent per booking/quote; retries resume the same attempt when possible. If an intent must be replaced, retire the previous one and reconcile any later charge on it.
- Treat frontend SDK success as a signal to poll/reload booking status, not proof of appointment confirmation. Keep a `processing` experience while provider confirmation is outstanding. Public `paymentStatus` values are `unpaid`, `requiresAction`, `processing`, `succeeded`, `failed`, `cancelled`; map provider-specific states internally. Aggregate `refundStatus` values are `none`, `pending`, `partial`, `refunded`, `failed`; individual refund attempts retain their own processing state. A partially refunded payment is still a succeeded payment with a distinct refund total.
- Verify webhook signatures against the raw request body and configured environment-specific signing secret. Reject unverifiable requests. Persist a unique event inbox record before acknowledging receipt; process duplicates safely and retry failures. Check provider account/environment, intent identity, booking relation, amount and currency before applying business state.
- Events may arrive duplicated, delayed or reordered. Reconcile against the current provider object when needed, use monotonic terminal payment transitions and unique business-event keys, and lock the booking/payment rows during transition. Never let a late failure overwrite a verified success. Confirm booking, record payment and enqueue the notification in one local transaction.
- Resolve expiry/payment races under the same booking/interval locking rules. If a success is verified while the hold is valid and the interval is reserved, confirm once. If the booking has already expired/cancelled or the interval was released, record the real successful payment without resurrecting the booking or taking another client's slot. Create a durable refund/reconciliation task and expose `resolutionRequired` or equivalent client-safe status. The default proposal is a full refund for an unfulfillable late payment; the firm must approve the operational policy. Until refunded, represent funds as received with refund pending, not as failed payment.
- Distinguish provider payment time from event arrival time. The system cannot safely assume a delayed success deserves a released slot; it must resolve money separately when reservation ownership no longer exists. A recovery path can offer a new booking only with explicit client acceptance and a separate record.
- Refunds are durable, permission-checked and idempotent. Validate amount against captured funds minus successful/pending refunds under a lock. Record requested/pending/succeeded/failed states; API acceptance is not proof the customer has received funds. Include retries and an operational queue for persistent failures. Cancellation determines booking state immediately according to policy; refund progress is independent.
- Run periodic reconciliation for stale payment attempts, unprocessed events, late success, pending refunds and mismatched totals. Compare provider objects with local records, repair only safe deterministic differences, and route ambiguous cases to staff with audit trails. Do not make webhook delivery the only way to recover correctness.

Implementation reference points: [Stripe PaymentIntents](https://docs.stripe.com/payments/payment-intents) and [Stripe webhooks](https://docs.stripe.com/webhooks). The requirements above define the proposed application's behavior; they do not establish current legacy backend behavior or the firm's commercial rules.

## 9. Intake, notifications and operations

Intake access is purpose-limited to the booking owner, assigned lawyer and specifically authorized staff. Do not include legal narratives in URLs, analytics, routine logs, email subjects, payment metadata or general administrator tables. Store encrypted data at rest through the selected infrastructure, use TLS in transit, and record sensitive staff access. Remove the old form's prechecked declaration behavior; any required acknowledgement must be actively accepted with its actual content/version and timestamp.

An email address and account profile provide the initial identity. A booking must include a supported language and consultation mode so the server can validate lawyer eligibility; the UI may preselect a supported choice from the profile/service. Phone and brief matter summary remain optional unless a specific service has a justified, reviewed requirement. Structured expansion requires firm review; uploads are deferred. Supporting bilingual UI does not imply every lawyer can consult in both languages; expose approved lawyer/service language capabilities.

Use a transactional outbox for verification, password reset, booking confirmation, reminders, cancellation and refund updates. Enforce unique business-event keys locally, use provider idempotency when available, retry with backoff and route persistent delivery failure to operations. A crash after sending but before recording success leaves an uncertain send; reconcile provider delivery identifiers before retrying when possible. Do not claim exactly-once network/email delivery. A mail failure must not roll back a confirmed payment or cause another charge. Messages link to the authenticated portal and contain only the minimum appointment metadata; generated meeting links use the approved provider and are restricted to participants. Consultation mode and video/calendar provider remain open decisions.

The worker handles hold expiry, outbox delivery, provider inbox retries, payment/refund reconciliation and reminder scheduling. Jobs are safe to replay, have bounded retries and persist their state. Recalculate pending reminders when a booking is cancelled or moved. Expose queue age/failure metrics and a safe staff retry operation rather than requiring manual database edits.

Minimum staff tooling before launch must support lawyer/service configuration, availability exceptions, booking search/assignment within permission bounds, cancellation with reason, completion/no-show, payment/refund exception review and audited retries. Staff operations need their own reviewed API contract; the initial client OpenAPI is not sufficient for production operations.

## 10. Operability, configuration and delivery

- Separate development, test/staging and production data, provider credentials, webhook secrets and email delivery. Use synthetic seed accounts, services, calendars and prices. Commit only environment variable names/placeholders; no legacy tokens or provider keys.
- Configure public frontend origin, allowed origins, database/queue connection, session/CSRF secrets, provider secrets, email templates/sender, enabled locales/currencies, office timezone, hold/lead-time/buffer rules and cancellation policy version. Branding stays out of durable IDs and business logic.
- Supply migrations, reproducible local setup, seed/reset instructions, an environment example, health/readiness endpoints, worker runbook and deployment/rollback procedure. Rollouts must tolerate compatible contract/database transitions across frontend, API and worker versions.
- Emit structured logs, trace/request IDs and metrics for latency/errors, booking conflicts, hold expiry, stale payment states, webhook failures, refund exceptions and notification backlog. Redact passwords, cookies, tokens, provider client secrets and intake content. Health checks reveal no secrets or legal/client data.
- Define agreed service objectives, capacity and backup recovery targets before launch; load-test the expected concurrency and retain measured results. Rehearse restore of database and required job/idempotency state, then verify booking and payment reconciliation after restoration. Avoid unsupported uptime or throughput claims in the plan.
- Establish account/data retention and deletion/export procedures with the firm. Keep financial audit and legal-intake retention decisions explicit and separate; this document does not assert a jurisdiction-specific legal retention period.
- Legacy import is optional, pending an inventory of actual existing data, ownership and mapping. Preserve IDs only via an explicit mapping table, validate timestamps/currency/consent provenance and rehearse imports in isolation. Fresh Git history does not migrate or erase a remote database.

## 11. Acceptance criteria and staged delivery

| Stage | Required acceptance evidence |
| --- | --- |
| A — Contract and foundation | Shared OpenAPI and synthetic fixtures pass validation; local API/worker/database start from documented instructions; migrations run on an empty store; deployment health checks work without secrets in the repo. |
| B — Identity and catalogue | Register/verify/login/logout/recovery work; reset tokens cannot be reused; revoked/expired sessions fail; missing/wrong CSRF or untrusted origins fail; unknown users do not leak through recovery; published service translations and eligibility are enforced. |
| C — Reservations | Concurrent overlapping requests leave exactly one booking for a lawyer; idempotent replay leaves one record; changed payload/key reuse conflicts; timezone/DST and hold expiry tests pass; clients cannot read/change another client's booking or set price/status/owner. |
| D — Intake and payment | Only owner/assigned lawyer/permitted staff see intake; reload resumes the booking/payment; decline/action-required/processing paths work; duplicate/reordered/bad-signature events cannot double-confirm; amount/currency mismatch is quarantined; success after expiry/cancellation creates a resolution/refund task without reopening the slot. |
| E — Operations and release | Staff complete cancellation/refund/completion/no-show workflows; double-refund attempts fail safely; payment creation crash recovery and provider reconciliation pass; notifications deduplicate; mail/provider outages recover; backup restore is rehearsed; agreed performance and business policies are signed off. |

Automate unit tests for pure pricing/state/permission rules, integration tests against the real database transaction design, contract producer/consumer checks and provider-sandbox workflow tests. Use a controlled clock and synthetic data for expiry/DST cases. End-to-end tests must cover successful consultation booking, availability conflict, payment requiring action, delayed webhook, cancellation and unauthorized access. Mock-only tests cannot prove concurrency, database constraints or provider signature handling.

Frontend can build every state against shared fixtures after Stage A; backend proceeds through B–E in parallel. Final branding and asset production do not block schema/scheduling work. Real prices, jurisdictions, required intake, refund policy, staff operations and production provider configuration are release gates, not facts to infer from the old UI.
